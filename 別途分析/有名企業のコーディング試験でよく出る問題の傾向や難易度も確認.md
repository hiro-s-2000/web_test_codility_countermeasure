難関テック企業・メガベンチャーの中途採用（特にCodilityが採用されているポジション）におけるコーディングテストは、「奇抜な難問は出ないが、計算量（パフォーマンス）とエッジケースへの配慮がシビア」という特徴があります。

全体像と頻出ジャンル、そしてタイピング量を抑えながら高得点を取るためのポイントを整理します。

---

### 1. 全体の構成と難易度目安

ポジション（サーバーサイド、フロントエンド、インフラ、データなど）によって問題数や組み合わせは若干異なりますが、Codility形式では以下の構成が一般的です。

| 項目 | 内容・目安 |
| --- | --- |
| **問題数・制限時間** | **2〜3問 ／ 90分〜120分程度**（1問あたり30〜40分ペース） |
| **難易度レベル** | **LeetCode の Easy 〜 Medium**（AtCoderなら **B 〜 C問題、一部D問題** 相当） |
| **言語** | 問題文は日本語（一部英語選択可）ですが、Codilityの仕様に準拠します |
| **合格ラインの目安** | 満点である必要はありませんが、**全体で70%〜80%以上のスコア**が安全圏とされています |

---

### 2. よく出る3つの問題パターン

難関テック企業・メガベンチャーのCodilityテストでは、高度な数学的知識やマニアックなアルゴリズム（複雑な動的計画法や高度なグラフ理論など）はほとんど出ません。代わりに以下の3パターンが頻出です。

#### ① 配列・文字列の操作と「計算量 $O(N)$ への最適化」

* **傾向:** 「配列の中から条件を満たすペアを探す」「文字列を特定のルールで変換・集計する」といった問題です。
* **最大のポイント:** 愚直に二重ループ（`for` の中に `for`）を書くと計算量が $O(N^2)$ になり、機能テスト（Correctness）は通っても、**巨大データに対するパフォーマンステスト（Performance）でタイムアウト（TLE）して点が半分しか入らない**作りになっています。
* **対策:** 二重ループを避けるための「ハッシュマップ（辞書・連想配列）」「セット（集合）」「累積和」「ソートして二分探索 / 尺取り法」の4つは必ず使えるようにしておく必要があります。

#### ② 仕様読解・シミュレーション系（実装問題）

* **傾向:** 問題文が少し長く、「特定の業務ルールやゲームのルールに従って処理を実行し、最終的な状態を返す」という問題です。
* **最大のポイント:** アルゴリズムのひらめきは不要ですが、条件分岐（`if-else`）が複雑になりやすく、焦って書き始めるとバグの温床になります。
* **対策:** 難関テック企業・メガベンチャーの選考官も公式インタビューで「処理が複雑になる場合は、1つの関数にベタ書きせず、小さなヘルパー関数に分けるなど可読性・保守性を意識しているかを見ている」と明言しています。条件判定だけを別関数に切り出すと、デバッグもタイピングも圧倒的に楽になります。

#### ③ 職種特化の問題（SQL や データ処理など）

* バックエンドやデータ関連のポジションでは、3問のうち1問がSQL（GROUP BY、JOIN、ウィンドウ関数など）になるケースがあります。普段ORMばかり使っていると生のSQLの構文を忘れがちなので、事前に基本構文だけ復習しておくと安心です。

### 3. Codility特有の「見えないテストケース」の罠

Codilityで最も気をつけるべきなのが、「Submit（提出）ボタンを押した後にしか走らないテストケース」の存在です。

画面上の「Run」ボタンを押したときに走るサンプルテストは2〜3個しかなく、それに通ったからといって安心はできません。提出後には以下のような意地悪なエッジケース（境界値）が自動で数十個テストされます。

* 配列の要素数が **最小（0個や1個）** のとき
* 配列の要素が **すべて同じ値**、または **すべてマイナス** のとき
* 計算結果が巨大になり、**32bit整数（`int`）の上限を超えてオーバーフロー**するとき

**【タイピングを増やさずスコアを守るコツ】**
関数の1行目に、以下のような「極端な入力が来たら即座に返すガード節」を1〜2行入れておくだけで、エッジケースの減点を防げます。

```python
if not arr: return 0

```

これならタイプ数もわずか十数文字で済み、選考官からも「エッジケースに配慮できる堅実なエンジニアだ」と高く評価されます。
