## Task 1：リッチテキストエディタのUndo/Redo＆数値スタック操作

### 🚨 採点・エッジケースの罠
1. **空白文字列・連続スペースへの耐性**: `S.isBlank()` のときや、最後にスタックが空になったときに忘れず `-1` を返す。
2. **20bit上限値 `1,048,575`（`0xFFFFF`）の境界チェック**: `+` の結果が `1_048,575` を超えた瞬間、または `-` の結果が `0` 未満になった瞬間に早期リターンで `-1` を返す。

### ⭕ 100%満点＆高速打鍵（2行プリミティブスタック＋ローカル関数）Kotlin模範解答
```kotlin
private const val LIM = 1_048_575

fun solution(S: String): Int {
    // 1. ガード節
    if (S.isBlank()) return -1

    // 2. プリミティブ配列スタック st とポインタ top で高速処理
    val toks = S.trim().split(' ')
    val st = IntArray(toks.size)
    var top = 0

    for (t in toks) {
        if (t.isEmpty()) continue
        when (t) {
            "POP" -> {
                if (top < 1) return -1
                top--
            }
            "DUP" -> {
                if (top < 1) return -1
                st[top] = st[top - 1]
                top++
            }
            "+" -> {
                if (top < 2) return -1
                val a = st[--top]
                val b = st[--top]
                if (a + b > LIM) return -1
                st[top++] = a + b
            }
            "-" -> {
                if (top < 2) return -1
                val a = st[--top]
                val b = st[--top]
                if (a - b < 0) return -1
                st[top++] = a - b
            }
            else -> {
                val v = t.toIntOrNull() ?: return -1
                if (v !in 0..LIM) return -1
                st[top++] = v
            }
        }
    }

    // 3. 最後にスタックが空なら -1、そうでなければ先頭を返す
    return if (top > 0) st[top - 1] else -1
}
```

### 🎤 1次面接（Android面接官）からの尋問と100点回答
- **Q. もしこのコマンド実行器をAndroidアプリのエディタ画面の「Undo / Redo機能」として拡張するなら、どのような設計パターン（Design Pattern）を採用しますか？**
  - **A.** **Commandパターン**（またはKotlinの `sealed interface EditorCommand`）を採用します。各操作を `execute()` と逆操作 `undo()`（またはイミュータブルな状態のスナップショット差分）を持つ `sealed interface` として表現し、`undoStack` と `redoStack` の2つの `ArrayDeque` で管理します。新規操作が行われたタイミングで `redoStack.clear()` を行うことで、ViewModel内で安全にUndo/Redo状態遷移をテスト可能にします。

## Task 2：動画プレイヤー同時視聴セッションのピーク帯域計測

### 🚨 採点・エッジケースの罠
1. **同時刻の開始と終了の順序**: 閉区間 $[start, end]$ なので、終了イベントの時刻を `endTimes[i] + 1L` として半開区間 $[start, end + 1)$ に変換し、`TreeMap<Long, Long>`（またはソート）で時刻順に累積すると同時刻の順序問題が綺麗に消え、コードもわずか15行で書けます！

### ⭕ 100%満点＆高速打鍵（半開区間＋TreeMap差分集計）Kotlin模範解答
```kotlin
import java.util.TreeMap

fun solution(startTimes: IntArray, endTimes: IntArray, bandwidths: IntArray): Long {
    // 1. ガード節
    val n = startTimes.size
    if (n == 0) return 0L

    // 2. 閉区間 [s, e] を半開区間 [s, e + 1) の差分として TreeMap mp に記録
    val mp = TreeMap<Long, Long>()
    for (i in 0 until n) {
        val s = startTimes[i].toLong()
        val e = endTimes[i].toLong() + 1L
        val bw = bandwidths[i].toLong()
        mp[s] = (mp[s] ?: 0L) + bw
        mp[e] = (mp[e] ?: 0L) - bw
    }

    // 3. 時刻順に累積和 cur を取り、最大値 ans を求める
    var cur = 0L
    var ans = 0L
    for (d in mp.values) {
        cur += d
        ans = maxOf(ans, cur)
    }
    return ans
}
```

### 🎤 1次面接（Android面接官）からの尋問と100点回答
- **Q. 閉区間 `[start, end]` の終了イベントを `end + 1L` に変換したのはなぜですか？**
  - **A.** 閉区間のままだと、同じ時刻 $T$ に複数の開始イベントと終了イベントが重なった際、「その瞬間のピーク」を正しく測るためにソートのタイブレーク条件や同一時刻のまとめ処理が複雑になり、Off-by-oneバグの温床になるためです。時刻が整数であることを活かし、終了を `end + 1L`（時刻 $end$ が終わった直後に帯域を解放する）という半開区間 $[start, end + 1)$ に正規化することで、単純な時刻順の累積和としてバグなく計算できます。

## Task 3：スタンプ透過キャンバスの最大パーツ面積と独立領域カウント

### 🚨 採点・エッジケースの罠
1. **再帰DFSによる `StackOverflowError`**: $H \times W = 200,000$ のキャンバス全体がジグザグに1つに繋がっているテストケースが裏側に必ず入っています。`val q = IntArray(h * w)` の2行キューで非再帰BFSを書くのが鉄則です。

### ⭕ 100%満点＆高速打鍵（1次元エンコード＋2行キューBFS）Kotlin模範解答
```kotlin
private val DR = intArrayOf(-1, 1, 0, 0)
private val DC = intArrayOf(0, 0, -1, 1)

fun solution(canvas: Array<IntArray>): Long {
    // 1. ガード節
    val h = canvas.size
    if (h == 0) return 0L
    val w = canvas[0].size
    if (w == 0) return 0L

    // 2. 訪問配列 vis とプリミティブ配列キュー q を用意
    val vis = BooleanArray(h * w)
    val q = IntArray(h * w)
    var ans = 0L

    // 3. 各連結成分を非再帰BFSで走査し、不透明度合計 cur の最大値を更新
    for (r0 in 0 until h) {
        for (c0 in 0 until w) {
            val s = r0 * w + c0
            if (vis[s] || canvas[r0][c0] <= 0) continue

            var hd = 0
            var tl = 0
            vis[s] = true
            q[tl++] = s
            var cur = 0L

            while (hd < tl) {
                val u = q[hd++]
                val r = u / w
                val c = u % w
                cur += canvas[r][c].toLong()

                for (d in 0..3) {
                    val nr = r + DR[d]
                    val nc = c + DC[d]
                    if (nr in 0 until h && nc in 0 until w) {
                        val nxt = nr * w + nc
                        if (!vis[nxt] && canvas[nr][nc] > 0) {
                            vis[nxt] = true
                            q[tl++] = nxt
                        }
                    }
                }
            }
            ans = maxOf(ans, cur)
        }
    }
    return ans
}
```

### 🎤 1次面接（Android面接官）からの尋問と100点回答
- **Q. もし入力配列 `canvas` を直接書き換えてもよい仕様だった場合、`vis` 配列をなくして空間計算量をさらに減らせますか？ 実務ではどう判断しますか？**
  - **A.** はい、アルゴリズム単体としては、訪問済みのピクセルを `canvas[nr][nc] = 0`（透過）に上書きしてしまえば、`vis: BooleanArray` のメモリすら不要になります。ただし実務のAndroid開発においては、引数で渡された配列（UIやBitmapバッファの元データ）を関数内で破壊的に変更（Mutate）すると、呼び出し元の再描画などで予期せぬ副作用バグを引き起こすため、不変性（Immutability）を守って別配列 `vis` を用意する設計を優先します。面接の場ではこのトレードオフを両方説明するのがベストです。
