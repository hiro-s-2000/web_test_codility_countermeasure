## Task 1：【Bugfixing】通知バッジの最長連続アクティブ日数（最大2行修正）

### 🔍 バグの特定プロセス

    var currentSpan = 0

### 🎤 1次面接での深掘り尋問と回答
- **質問**: 「もし変更可能な行数が『1行だけ（at most 1 line）』という制約だったら、どう直しますか？」
- **100点回答**:
  「`if (A[i] == 1)` のブロック内で毎回 `maxSpan` を更新する必要がありますが、そもそもループが `1 until A.size` になっている時点で `A = [1]` のケースが救えません。したがって、CodilityのBugfixingで2箇所の独立した境界バグ（先頭要素のスキップと末尾区間の未反映）がある場合は必ず『at most 2 lines』の制約になっており、問題文の『at most K lines』の $K$ の値自体が『バグが何箇所あるかの最大のヒント』になります。」

## Task 2：【アルゴリズム（標準）】プッシュ通知の同一チャンネル・クールダウン制御

### ✅ 満点解答（Kotlin）
```kotlin
// 1. チャンネル毎の最終配信時刻をMap管理
// 2. T[i] - lastTime >= D の時だけカウント＆更新
fun solution(T: IntArray, C: IntArray, D: Int): Int {
    val n = T.size
    if (n == 0) return 0

    // 再ハッシュを防ぐため初期容量を指定したマップ mp
    val mp = HashMap<Int, Int>(n * 4 / 3 + 1)
    var ans = 0

    for (i in 0 until n) {
        val now = T[i]
        val ch = C[i]
        val prv = mp[ch]

        if (prv == null || now.toLong() - prv.toLong() >= D.toLong()) {
            ans++
            mp[ch] = now
        }
    }

    return ans
}
```

### 🎤 1次面接での深掘り尋問と回答
- **質問**: 「`time.toLong() - prevTime.toLong() >= D.toLong()` と `Long` にキャストしている理由は何ですか？ `T[i]` は正の整数なので `Int` のまま引き算してもオーバーフローしないのでは？」
- **100点回答**:
  「今回の制約では `T[i] >= 0` かつ `time >= prevTime` なので `Int` の減算でもオーバーフローはしませんが、もし1次面接の仕様変更で『タイムスタンプに負の相対時刻（エポック前）が含まれる』となった場合、`Int` 同士の減算は容易にオーバーフローします。また、もし条件式を `time >= prevTime + D` と移項して書いた場合、`prevTime + D` が $10^9 + 10^9 = 2 \times 10^9 \approx \text{Int.MAX\_VALUE}$ 付近でオーバーフローする危険があるため、時刻差分の比較では常に `Long` に引き上げる防御的コーディングを徹底しています。」

## Task 3：【アルゴリズム（応用）】オフライン記事パックの分割ダウンロード最小帯域幅

### ✅ 満点解答（Kotlin・答えで二分探索）
```kotlin
// 1. 下限 lo = max(S), 上限 hi = sum(S) で二分探索
// 2. ローカル関数 ok(lim) で K ブロック以内に収まるか判定
fun solution(K: Int, S: IntArray): Long {
    val n = S.size
    if (n == 0) return 0L

    var lo = 0L
    var hi = 0L
    for (x in S) {
        val v = x.toLong()
        if (v > lo) lo = v
        hi += v
    }
    if (K >= n) return lo
    if (K == 1) return hi

    fun ok(lim: Long): Boolean {
        var cnt = 1
        var cur = 0L
        for (x in S) {
            val v = x.toLong()
            if (cur + v > lim) {
                cnt++
                cur = v
                if (cnt > K) return false
            } else {
                cur += v
            }
        }
        return true
    }

    var ans = hi
    while (lo <= hi) {
        val mid = (lo + hi) ushr 1
        if (ok(mid)) {
            ans = mid
            hi = mid - 1L
        } else {
            lo = mid + 1L
        }
    }
    return ans
}
```

## Task 4：【Android実務実装①】ViewModel + Coroutines + StateFlow 実装

### ✅ 満点解答（Kotlin）
```kotlin
import androidx.lifecycle.ViewModel
import androidx.lifecycle.viewModelScope
import java.util.concurrent.ConcurrentHashMap
import kotlinx.coroutines.CancellationException
import kotlinx.coroutines.CoroutineDispatcher
import kotlinx.coroutines.Dispatchers
import kotlinx.coroutines.Job
import kotlinx.coroutines.flow.MutableStateFlow
import kotlinx.coroutines.flow.StateFlow
import kotlinx.coroutines.flow.asStateFlow
import kotlinx.coroutines.launch

class ArticleSearchViewModel(
    private val repository: ArticleRepository,
    private val dispatcher: CoroutineDispatcher = Dispatchers.Main
) : ViewModel() {

    private val _uiState = MutableStateFlow<SearchUiState>(SearchUiState.Idle)
    val uiState: StateFlow<SearchUiState> = _uiState.asStateFlow()

    private val cache = ConcurrentHashMap<String, List<Article>>()
    private var searchJob: Job? = null

    fun onQuerySubmitted(rawQuery: String, forceRefresh: Boolean = false) {
        val query = rawQuery.trim()

        // 1. 2文字未満のバリデーション
        if (query.length < 2) {
            searchJob?.cancel()
            _uiState.value = SearchUiState.Error(query, "Query too short")
            return
        }

        // 2. キャッシュヒット判定（forceRefresh == false の場合のみ）
        if (!forceRefresh) {
            val cached = cache[query]
            if (cached != null) {
                searchJob?.cancel()
                _uiState.value = if (cached.isEmpty()) {
                    SearchUiState.Empty(query)
                } else {
                    SearchUiState.Content(query = query, articles = cached, fromCache = true)
                }
                return
            }
        }

        // 3. 非同期検索の実行（進行中の古いJobはキャンセル）
        searchJob?.cancel()
        searchJob = viewModelScope.launch(dispatcher) {
            _uiState.value = SearchUiState.Loading
            try {
                val result = repository.searchArticles(query)
                // 防御的コピーでイミュータブル化してキャッシュ保存
                val immutableResult = result.toList()
                cache[query] = immutableResult

                _uiState.value = if (immutableResult.isEmpty()) {
                    SearchUiState.Empty(query)
                } else {
                    SearchUiState.Content(
                        query = query,
                        articles = immutableResult,
                        fromCache = false
                    )
                }
            } catch (e: CancellationException) {
                // コルーチンの構造化並行性を守るため必ず再スロー
                throw e
            } catch (e: Exception) {
                _uiState.value = SearchUiState.Error(
                    query = query,
                    message = e.message ?: "Network error"
                )
            }
        }
    }

    fun clearCache() {
        searchJob?.cancel()
        cache.clear()
        _uiState.value = SearchUiState.Idle
    }
}
```

### 🎤 1次面接での深掘り尋問と回答
- **質問**: 「ユーザーがEditTextで1文字打つたびに検索が走る場合、この `onQuerySubmitted` をそのまま呼ぶとどうなりますか？ 実務ならどう改善しますか？」
- **100点回答**:
  「1文字ごとに `searchJob?.cancel()` と新規通信が走るため、無駄なネットワークリクエストが大量発生します。実務では検索クエリを `MutableStateFlow<String>` として受け取り、Flowパイプラインで `.debounce(300L)` → `.map { it.trim() }` → `.distinctUntilChanged()` → `.flatMapLatest { query -> ... }` と繋ぐことで、タイピングが300ms止まった時点の最新クエリだけを自動的にスイッチングして検索するリアクティブ設計にします。」

## Task 5：【Android実務実装②】OkHttp 認証＆レート制限リトライ Interceptor の実装

### ✅ 満点解答（Kotlin）
```kotlin
import okhttp3.Interceptor
import okhttp3.Request
import okhttp3.Response

class ResilientAuthInterceptor(
    private val authSessionManager: AuthSessionManager
) : Interceptor {

    override fun intercept(chain: Interceptor.Chain): Response {
        val originalRequest = chain.request()

        // 1. 現在のトークンを付与して初回リクエスト実行
        val firstRequest = buildRequestWithToken(
            originalRequest,
            authSessionManager.getCurrentToken()
        )
        val firstResponse = chain.proceed(firstRequest)

        // 2. 503 Service Unavailable の場合：1回だけ即時リトライ
        if (firstResponse.code == 503) {
            firstResponse.close()
            return chain.proceed(firstRequest)
        }

        // 3. 401 Unauthorized の場合：トークンリフレッシュ＆1回リトライ
        if (firstResponse.code == 401) {
            val refreshedToken = authSessionManager.refreshToken()
            if (refreshedToken.isNullOrEmpty()) {
                authSessionManager.onSessionExpired()
                return firstResponse
            }

            // ★重要：リトライ前に必ず最初のレスポンスボディをクローズする
            firstResponse.close()

            val retryRequest = buildRequestWithToken(originalRequest, refreshedToken)
            val retryResponse = chain.proceed(retryRequest)

            if (retryResponse.code == 401) {
                authSessionManager.onSessionExpired()
            }
            return retryResponse
        }

        return firstResponse
    }

    private fun buildRequestWithToken(request: Request, token: String?): Request {
        if (token.isNullOrEmpty()) return request
        return request.newBuilder()
            .header("Authorization", "Bearer $token")
            .build()
    }
}
```

### 🎤 1次面接での深掘り尋問と回答
- **質問**: 「マルチスレッドで同時に3つのAPIリクエストが飛んで、3つとも同時に `401` が返ってきた場合、この実装だと `refreshToken()` が3回呼ばれてしまいませんか？ 実務の大規模トラフィックの商用アプリならどう防ぎますか？」
- **100点回答**:
  「ご指摘の通り、並列リクエスト時にすべてが `401` を受けると `refreshToken()` が多重実行され、サーバー側でトークンローテーションエラーになる危険があります。
  実務では2つの改善を行います。
  1つ目は、リフレッシュ処理を `synchronized(lock)`（またはコルーチンなら `Mutex`）で排他制御し、ロック獲得後に『リクエスト送信時のトークン』と『現在の最新トークン（`getCurrentToken()`）』を比較する **Double-Checked Locking** を入れることです。すでに別スレッドが更新済みなら `refreshToken()` を呼ばずに新しいトークンで即リトライします。
  2つ目は、OkHttpの通常の `Interceptor` ではなく、401専用の **`okhttp3.Authenticator`** インターフェースに分離することです。」
