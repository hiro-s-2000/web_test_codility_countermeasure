## Task 1：プッシュ通知プレビューの単語境界トランケート

### 🚨 採点・エッジケースの罠（ここを落とすと60%に減点）
1. **`K` が非常に小さいケース**: `K < 3` のとき `"..."` すら入らないため `""` を返す必要がある。
2. **全文がちょうど `K` 文字のケース**: `message.length <= K` のときは `"..."` を付けてはいけない（そのまま返す）。
3. **先頭の1単語が長すぎるケース**: 例えば `message = "Notification"`, `K = 8` のとき、`"Notification ..."` は16文字で入らないため、1単語も採用できず `"..."` のみを返す。

### ⭕ 100%満点＆高速打鍵（3文字略語）Kotlin模範解答
```kotlin
fun solution(message: String, K: Int): String {
    // 1. ガード節 (K<3 / 全文収まる / K==3)
    if (K < 3) return ""
    if (message.length <= K) return message
    if (K == 3) return "..."

    // 2. " ..." の4文字を引いた上限 lim まで単語を詰める
    val lim = K - 4
    val sb = StringBuilder(K)

    for (w in message.split(' ')) {
        val sep = if (sb.isEmpty()) 0 else 1
        if (sb.length + sep + w.length > lim) break
        if (sep > 0) sb.append(' ')
        sb.append(w)
    }

    // 3. 1単語も入らなければ "..."、入れば " ..." を付与
    return if (sb.isEmpty()) "..." else sb.append(" ...").toString()
}
```

### 🎤 1次面接（Android面接官）からの尋問と100点回答
- **Q. なぜ文字列連結に `+` ではなく `StringBuilder(K)` を使い、初期容量 `K` を指定したのですか？**
  - **A.** ループ内で `String` の `+` 連結を行うとイミュータブルな文字列インスタンスが毎回生成されて $O(N^2)$ のコピーコストとGCゴミが発生します。また、結果の文字列長は必ず `K` 以下になることが保証されているため、`StringBuilder(K)` と初期バッファ容量を指定することで、内部 `char[]` の再確保（Resize）すら0回に抑えています。
- **Q. Androidの実務で通知やTextViewの省略表示を行う場合、このような文字数カウントだけで十分ですか？**
  - **A.** 実務のAndroid UIでは、文字数と表示幅（ピクセル数）は一致せず、また絵文字（結合文字・書記素クラスタ：Grapheme Cluster）を `String.length`（UTF-16コード単位）で切ると文字化けします。そのため実務では `TextView` / Compose `Text` の `TextOverflow.Ellipsis` や `StaticLayout` を使うか、文字単位で扱う必要がある場合は `BreakIterator.getCharacterInstance()` を使ってサロゲートペアや絵文字を破壊しないように切り詰めます。

## Task 2：チャットストリームのスパムバースト検知

### 🚨 採点・エッジケースの罠
1. **`timestamps[r] - timestamps[l]` の計算**: 差がちょうど `windowMs` と等しい場合も区間内に含まれる（`>` のときだけ左端を進める）。
2. **`windowMs = 0` のケース**: 同じミリ秒に複数のメッセージが送信されている場合、それらは同一ウィンドウに入る。
3. **コレクションのBoxing罠**: `senderIds[i] <= 100,000` という制約があるため、**`IntArray(mxId + 1)`** を頻度テーブル `cnt` に使うとボクシングゼロかつ最短コードで圧倒的に高速になります。

### ⭕ 100%満点＆高速打鍵（3文字略語）Kotlin模範解答
```kotlin
fun solution(timestamps: IntArray, senderIds: IntArray, windowMs: Int): Int {
    // 1. ガード節 (0/1要素)
    val n = timestamps.size
    if (n <= 1) return n

    // 2. 送信者IDの最大値 mx を求め、出現回数配列 cnt を用意
    var mx = 0
    for (id in senderIds) if (id > mx) mx = id
    val cnt = IntArray(mx + 1)

    // 3. 尺取り法 (l, r) でウィンドウ内のユニーク送信者数 cur を追跡
    var l = 0
    var cur = 0
    var ans = 0
    val win = windowMs.toLong()

    for (r in 0 until n) {
        val rId = senderIds[r]
        if (cnt[rId]++ == 0) cur++

        while (l <= r && timestamps[r].toLong() - timestamps[l].toLong() > win) {
            val lId = senderIds[l++]
            if (--cnt[lId] == 0) cur--
        }
        ans = maxOf(ans, cur)
    }
    return ans
}
```

### 🎤 1次面接（Android面接官）からの尋問と100点回答
- **Q. もし `senderIds[i]` が `1〜100,000` ではなく、64bitのランダムなUUIDや長大なユーザーIDだったらどう変更しますか？**
  - **A.** IDの値域が広い（スパースな）場合は、添字配列にするとメモリ上限を超えてしまうため、`cnt` を初期容量指定の `HashMap<Long, Int>(n * 4 / 3 + 1)`（Android SDK環境なら `LongSparseArray` や AndroidX Collection の `MutableLongIntMap`）に差し替えます。

## Task 3：オフラインイベントログのバッチ分割アップロード

### 🚨 採点・エッジケースの罠
1. **オーバーフローの罠**: `payloadSizes[i]` が最大 $10^9$、要素数が $10^5$ のため、合計値は最大 $10^{14}$ となり `Int` では確実にオーバーフローします。すべて `Long` で計算する必要があります。
2. **単一要素のコスト**: 1つのイベント $i$ をバッチに入れたときの増加コストは `payloadSizes[i].toLong() + hdr` です。

### ⭕ 100%満点＆高速打鍵（ローカル関数 `fun ok()` 活用）Kotlin模範解答
```kotlin
fun solution(maxBatches: Int, headerOverhead: Int, payloadSizes: IntArray): Long {
    // 1. ガード節
    if (payloadSizes.isEmpty()) return 0L

    // 2. 二分探索の下限 lo と上限 hi を算出
    val hdr = headerOverhead.toLong()
    var lo = 0L
    var hi = 0L
    for (sz in payloadSizes) {
        val c = sz.toLong() + hdr
        if (c > lo) lo = c
        hi += c
    }
    if (maxBatches >= payloadSizes.size) return lo
    if (maxBatches == 1) return hi

    // ローカル関数: 1バッチ上限 lim 以下で maxBatches 個以内に収まるか判定
    fun ok(lim: Long): Boolean {
        var cnt = 1
        var cur = 0L
        for (sz in payloadSizes) {
            val c = sz.toLong() + hdr
            if (cur + c > lim) {
                cnt++
                cur = c
                if (cnt > maxBatches) return false
            } else {
                cur += c
            }
        }
        return true
    }

    // 3. 答えで二分探索
    var ans = hi
    while (lo <= hi) {
        val mid = (lo + hi) ushr 1
        if (ok(mid)) {
            ans = mid
            hi = mid - 1L
        } else {
            lo = mid + 1L
        }
    }
    return ans
}
```

### 🎤 1次面接（Android面接官）からの尋問と100点回答
- **Q. このログのバッチ分割送信を実際のAndroidアプリ（WorkManager等）で実装する場合、どのような点に気をつけますか？**
  - **A.** 実務では、①アプリプロセスが途中でKillされてもログが消えないよう、まずRoom（SQLite）に永続化し、送信ステータス（Pending / Uploading / Synced）を管理すること、② `WorkManager` の `Constraints` でネットワーク接続時（`NetworkType.CONNECTED`）やバッテリー低下時回避を設定し、失敗時は `Result.retry()` とExponential Backoffで再試行すること、③計算処理自体はUIスレッドをブロックしないよう `withContext(Dispatchers.Default)`（DB/通信は `Dispatchers.IO`）で実行することに留意します。
