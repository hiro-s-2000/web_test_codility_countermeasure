難関テック企業・メガベンチャーのAndroid（Kotlin）選考におけるコーディングテストおよび面接でのレビューでは、単にテストケースを通すこと以上に「数千万人が使う大規模・長寿命なプロダクトを、複数人で安全に保守・拡張できるコードか」という視点がシビアに見られます。

テストが満点でもコードの質で落ちるケースがある一方、一部テストが通らなくても設計意図や可読性が高く評価されて通過するケースもあります。現場のエンジニアに嫌われる書き方と、好かれる（リーダブルとされる）コードの基準は以下の通りです。

---

## 1. 面接官（現場エンジニア）に嫌われる書き方

大規模開発においてバグの温床になりやすい書き方や、Kotlinの言語特性を活かせていない「Javaっぽいコード」は強いマイナス評価になります。

* **`!!`（非Nullアサーション）の乱用と雑なNull処理**
* 最も嫌われるポイントの一つです。テストを通すために安易に `!!` を使うと、「本番環境でNPE（NullPointerException）によるクラッシュを引き起こす人」と見なされます。


* **可変状態（`var` や `MutableList` など）の多用**
* スレッドセーフティや状態管理の複雑化を招くため、理由なく `var` を使ったり、外部に `Mutable` なコレクションをそのまま公開する設計は嫌われます。


* **全てを `main` や1つの関数に詰め込む手続き型コード**
* 時間制限がある中でも、100行を超えるような巨大関数や、ネストが3段・4段と深くなる `if-else` / `for` のゴリ押しは「構造化・抽象化ができない」と判断されます。


* **スコープ関数（`let`, `run`, `apply` 等）の誤用・ネスト**
* `?.let { ... ?: run { ... } }` のようにスコープ関数をチェインして「どっちのケースかわかりにくい三項演算子もどき」を作ったり、`it` が何を指すか分からなくなるネストは可読性を著しく下げるため嫌われます。


* **計算量（Time / Space Complexity）への無頓着**
* リストの検索で安易にループの中に `contains()`（$O(N^2)$）を書くなど、データ量が増えた際にUIフリーズ（ANR）やメモリリークを引き起こす書き方は厳しくチェックされます。


* **意図のわからない命名とマジックナンバー**
* `temp`, `data`, `list2`, `flag` といった抽象的すぎる変数名や、意味を持たない数値リテラルの直書きはレビューで必ず突っ込まれます。

## 2. 難関テック企業・メガベンチャーのAndroidエンジニアに好かれる「リーダブルコード」

難関テック企業・メガベンチャーのクライアント開発では、「Kotlinらしい表現力（Idiomatic Kotlin）」「イミュータブルな設計」「単一責任の原則」の3つを押さえたコードが好まれます。

### ① 不変性（Immutability）の徹底

* 原則すべて `val` で宣言し、コレクションも標準のイミュータブルな `List`, `Set`, `Map` を使います。
* 状態を変更する場合は、既存のオブジェクトを書き換えるのではなく、`data class` の `copy()` やコレクション操作関数を使って新しいインスタンスを返す（関数型アプローチ）書き方が好まれます。

### ② 宣言的なコレクション操作と早期リターン

手続き型のループ（インデックスを使った `for` 文と `var` の組み合わせ）ではなく、何を実現したいかが一目でわかる標準ライブラリ関数を使い分けます。

```kotlin
// ❌ 嫌われる書き方（手続き型・可変状態・ネストが深い）
fun getActiveUserNames(users: List<User>?): List<String> {
    val result = mutableListOf<String>()
    if (users != null) {
        for (i in 0 until users.size) {
            if (users[i].isActive && users[i].name != null) {
                result.add(users[i].name!!)
            }
        }
    }
    return result
}

// ⭕ 好かれる書き方（宣言的・イミュータブル・Null安全）
fun getActiveUserNames(users: List<User>?): List<String> {
    if (users.isNullOrEmpty()) return emptyList()

    return users
        .asSequence() // 要素数が多い場合の評価効率への配慮
        .filter { it.isActive }
        .mapNotNull { it.name }
        .toList()
}

```

### ③ 型システムによる状態の表現（ドメインモデリング）

Webテストの実装問題（API仕様やビジネスロジックの実装など）では、プリミティブ型（`String` や `Int`）のまま引き回すのではなく、**小さなクラスや `enum` / `sealed interface` に切り出す**と非常に高く評価されます。

* ステータス管理に `Int` や `String` を使わず、`enum class` や `sealed interface` を使い、`when` 式で網羅性（Exhaustiveness）をコンパイラに保証させる。
* 入出力のデータ構造を適切な `data class` に分離し、責務（パース処理、バリデーション、集計ロジックなど）ごとに関数やクラスを分ける。

### ④ エッジケースとスケーラビリティへの配慮

* **境界値・異常系のガード節:** 空配列、負数、上限値オーバー（`Int` で足りるか `Long` が必要か）などを関数の先頭で `require()` や早期 `return` で弾いているか。
* **適切なデータ構造の選択:** 検索が頻繁発生するなら `List` ではなく `Set` や `Map` に変換してから処理し、計算量を $O(N)$ や $O(1)$ に落としているか。

## 3. 面接の「コーディングレビュー」で評価を上げる立ち回り

1次・2次面接のレビューでは、提出したコードを画面共有しながら「なぜこう書いたのか」「今見返して改善したい点はあるか」をディスカッションします。

1. **提出前に「セルフレビューメモ」を作っておく**
Webテスト終了後、自分のコードを振り返り、「時間制限のためここは妥協したが、本来はこうリファクタリングしたい」「ここの計算量は $O(N \log N)$ だが、こういうデータ構造にすれば $O(N)$ にできる」という改善点を言語化しておきます。面接官から指摘される前に自分から言えると、シニアレベルの視点を持っている証明になります。
2. **「なぜそのコレクション/スコープ関数を選んだか」を説明できるようにする**
「なぜここは `List` ではなく `Sequence` にしたのか」「なぜ `ArrayList` ではなく `ArrayDeque` なのか」など、裏側のメモリ効率や動作原理を理解して書いていることを示せると強い好印象を残せます。
3. **テスタビリティ（テストのしやすさ）への言及**
レビュー時に「実際のプロダクトコードであれば、このロジックはViewModelやUseCaseから切り出してUnit Testが書けるように設計します」といった一言を添えると、実務での再現性が高く評価されます。
