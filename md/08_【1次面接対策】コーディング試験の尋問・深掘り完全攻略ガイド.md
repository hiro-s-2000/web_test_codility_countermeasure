1. **総合スコアと各Taskの内訳**:
   - Taskごとの **Correctness（正確性）** と **Performance（性能）** のパーセンテージ。
2. **タイムライン＆Playback（打鍵再生ログ）**:

3. **落としたテストケースの詳細（Failed Test Cases）**:

4. **最終提出コードの全文**:

### 1.2 なぜ「コードへの尋問」を行うのか？（面接官の3つの意図）
* **意図①（不正・AI代筆の炙り出し）**:
  AIが出力したコードを写経しただけの候補者は、「なぜ23行目でこの条件式が必要なのですか？」「ここを ` < ` から ` <= ` に変えるとどうなりますか？」と聞かれた瞬間に言葉に詰まります。**自分の言葉で設計意図を即答できれば、それだけでAI疑念は100%晴れます。**
* **意図②（実務エンジニアリング能力の測定）**:
  ただ動くだけの競技プログラミング的なコードではなく、「可読性・保守性・メモリ効率・エッジケースへの防御」を意識して書いているかを見ています。
* **意図③（フィードバック受容性とライブ修正力）**:
  試験本番の緊張下で一部のテストケースを落としていても、面接の場で「あ、ここは `Int` のオーバーフローを見落としていました。`Long` にキャストすれば解決します」と即座に自己診断・修正できれば、**減点どころかプラス評価に変わります。**

### 尋問パターン②：「なぜここで標準の `List` や関数型チェーン（`map`/`filter`）を使わず、`IntArray` や独自クラスを使ったのですか？」
**🎯 100点満点の回答テンプレート（JVMの内部仕様アピール）**:
> 「2つ理由があります。
> 1つ目は **JVM上のパフォーマンス（ボクシング回避）** です。Kotlinの `List<Int>` や `.map {}` チェーンを使うと、内部で `java.lang.Integer` へのオートボクシングと中間 `ArrayList` のアロケーションが発生し、要素数10万件規模ではGC負荷とメモリ消費が4〜5倍に膨らみます。そのため、プリミティブの `int[]` / `long[]` にコンパイルされる `IntArray` / `LongArray` を選択しました。
> 2つ目は **可読性とバグ防止** です。プリミティブ変数を複数フラットに並べると状態遷移のバグが起きやすいため、責務を明確にした `private class`（または `data class`）にカプセル化し、メインの `solution` 関数がビジネスロジックとして読めるように設計しました。」
> *(※ この回答ができる候補者は、中途採用の1次面接で圧倒的に高い評価を得られます)*

* **ケースB：マルチスレッド（並行リクエスト）から同時に呼ばれる場合**

### 📋 全19問（例題1〜3＋領域1〜12＋Bugfix＋Android実装3問）面接官の深掘り質問と模範回答集

#### 1. 累積XOR（`例題1_奇数回出現要素の特定_XOR.kt`）
* **Q. なぜ `HashMap` や `var` ループではなく `A.fold(0) { acc, x -> acc xor x }` を使ったのですか？**
  * **A.** `HashMap<Int, Int>` は空間計算量 $O(N)$ とボクシングが発生します。XORの性質（`x xor x = 0`）を `fold` で畳み込めば、追加メモリゼロの **Space $O(1)$** かつ可変変数 `var` を一切使わないイミュータブルな1行の式として書けるためです。

#### 2. すれ違う車のペア集計（`例題2_すれ違う車のペア集計_TrafficCounter.kt`）
* **Q. カウンタ `cnt` と `ans` を `Int` ではなく `Long`（`0L`）にしている理由は？**
  * **A.** 要素数 $N = 100,000$ のとき、ペアの最大数は約 $50,000 \times 50,000 = 2.5 \times 10^9$ となり、32bit符号付き整数（`Int.MAX_VALUE` $\approx 2.14 \times 10^9$）をオーバーフローして負数になるためです。また、`0` や `10億` のマジックナンバーは `EAST`, `LIM` として定数化し可読性を保っています。

#### 3. 尺取り法 / Two Pointers（`例題3_最小連続区間長_尺取り法.kt`）
* **Q. 外側に `for` ループがあり、内側に `while` ループがありますが、計算量は $O(N^2)$ になりませんか？**
  * **A.** なりません。右端ポインタ `r` が $0$ から $N-1$ まで最大 $N$ 回進み、左端ポインタ `l` も後戻りせず最大 $N$ 回しか進まないため、内側の `while` ループは全体を通して高々 $N$ 回しか実行されません。したがって償却計算量（Amortized Complexity）は **Time $O(N)$**、**Space $O(1)$** です。

#### 4. 累積和フラット化（`領域1_累積和_DNA区間最小影響度.kt`）
* **Q. 累積和配列 `acc` を2次元配列 `Array(4) { IntArray(N + 1) }` ではなく1次元 `IntArray((n + 1) * 4)` にしている理由は？**
  * **A.** JVMにおいて2次元配列は「配列オブジェクトへの参照配列」となり、メモリアドレスが連続しないためCPUキャッシュミスが起きやすくなります。1次元にフラット化することで1回の配列アロケーションで済み、同じインデックスの4種類のカウントがメモリ上で隣接するためキャッシュ局所性（Cache Locality）が高まります。

#### 5. プリミティブ配列スタック（`領域2_単調スタック_生き残る魚の数.kt`）
* **Q. 標準の `java.util.Stack` や `ArrayDeque<Int>` ではなく `val st = IntArray(n); var top = 0` でスタックを実装したのはなぜですか？**
  * **A.** `java.util.Stack` は全メソッドが `synchronized` で遅く、`ArrayDeque<Int>` もジェネリクス型のため `Integer` へのボクシングが発生します。最大10万要素のプリミティブ整数しか扱わない問題では、`IntArray` とポインタ `top` で管理する方がボクシングゼロで最速かつ省メモリなためです。実務でオブジェクトを扱う場合は初期容量を指定した `ArrayDeque<T>` を使います。

#### 6. Kadaneのアルゴリズム（`領域3_最大部分配列和_Kadane法.kt`）
* **Q. `cur` と `ans` の初期値を `0` ではなく `A[0].toLong()` にしている理由は？**
  * **A.** 「少なくとも1つの要素を含む連続部分配列」という制約があるため、もし配列の全要素が負数（例：`[-5, -2, -8]`）だった場合、`0` で初期化してしまうと空配列の和 `0` を誤って返してしまうためです。先頭要素 `A[0]` で初期化し、インデックス `1` から走査することで全要素負数のケースでも正しく `-2` を返せます。

#### 7. 答えで二分探索（`領域4_答えで二分探索_最大ブロック和の最小化.kt`）
* **Q. 判定関数 `fun ok(lim: Long)` をクラスメソッドではなく `solution` 内のローカル関数にした理由と、`(lo + hi) ushr 1` の意図は？**
  * **A.** Kotlinのローカル関数を使うことで、「貪欲判定の責務を別関数に分けて可読性を高める（単一責任の原則）」と同時に、外側の不変パラメータ `A` や `K` をクロージャとして参照できるため、引数の引き回しを省いて簡潔に書けるからです。また `ushr 1` は `lo + hi` の符号ビット反転を防いで安全に中央値を求めるJVMの定石イディオムです。

#### 8. イベントスイープ / 平面走査法（`領域5_平面走査法_円盤の交差ペア数.kt`）
* **Q. 円盤ごとのペア `(left, right)` をオブジェクトにせず、`lArr` と `rArr` を別々にソートして正しいペア数が求まるのですか？**
  * **A.** はい、正しく求まります。「どの円盤と交差したか」の個別特定は不要で、「新しい円盤の左端に到達した時点で、すでに開いていてまだ閉じていない円盤が何個あるか（`act`）」だけ分かればよいため、始点と終点を独立に `LongArray` でソートしても数学的に同値になり、オブジェクト生成をゼロに抑えられます。

#### 9. 非再帰Union-Find（`領域6_非再帰UnionFind_ネットワーク連結成分.kt`）
* **Q. `find(x)` を再帰ではなく `while` ループと `par[cur] = par[par[cur]]` で書いている理由は？**
  * **A.** グラフが一直線の縮退木になった場合、再帰だと深さが $O(N)$ になりJVMで `StackOverflowError` が発生するリスクがあるためです。`while` ループ内で1行経路圧縮（Path Halving: `par[cur] = par[par[cur]]`）を行うことで、コールスタックを一切消費せずにほぼ $O(\alpha(N))$ の高速検索を実現しています。

#### 10. 実務型ログパース（`領域7_実務型文字列ログ解析_通話料金集計.kt`）
* **Q. `S.lineSequence().mapNotNull { parse(it) }` と `data class CallLog` を使った意図を教えてください。**
  * **A.** 3点あります。1点目は `split("\n")` による全行リストの一括メモリ確保を避け、`lineSequence()` で遅延評価するためです。2点目は `toIntOrNull() ?: return null` と `mapNotNull` を組み合わせることで、不正なフォーマットの行があっても `!!`（非Nullアサーション）を一切使わずにNull安全にフィルタリングするためです。3点目は「パース処理 (`parse`)」「料金計算 (`cost`)」「集計」の責務を分離し、実務のコードレビュー基準に耐えるリーダブルな構造にするためです。

#### 11. 文字列スライディングウィンドウ（`領域8_文字列ウィンドウ_重複なし最長部分文字列.kt`）
* **Q. `HashMap<Char, Int>` ではなく `IntArray(256)` を使った理由と、絵文字（Unicode）が来たらどうするか教えてください。**
  * **A.** ASCII文字の範囲であればサイズ256の固定長 `IntArray` をダイレクトアドレシングテーブルとして使うことで、ハッシュ計算とボクシングを完全に排除でき、空間計算量も $O(1)$ になるためです。もし入力がサロゲートペアや絵文字を含む任意のUnicode文字列である場合は、初期容量を指定した `HashMap<Int, Int>`（コードポイント単位）または `BreakIterator` に切り替えます。

#### 12. 貪欲法と区間スケジューリング（`領域9_貪欲法_重複しない最大区間選択.kt`）
* **Q. 終端 `B[i]` でソートされているとなぜ先頭から貪欲に選ぶだけで最適解になるのですか？**
  * **A.** 「最も早く終わる区間（`B[i]` が最小の区間）」を選ぶことが、後続の区間のために残りのスケジュール空間を最大化するため（交換議論：任意の最適解の先頭区間を最も早く終わる区間に置き換えても悪化しないため）、$O(N)$ の1パス貪欲法で厳密な最適解が得られます。

#### 13. 2次元グリッド非再帰BFS（`領域10_2次元グリッド探索_非再帰BFS最短経路と島集計.kt`）
* **Q. なぜ再帰DFSではなくBFSにし、さらに座標 `(r, c)` を `r * w + c` に変換したのですか？**
  * **A.** 2次元グリッドの連結成分が大きく蛇行している場合、最大で $H \times W$（数十万）の深さの再帰が発生し、JVMでは確実に `StackOverflowError` でクラッシュします。また、BFSのキューに `Pair(r, c)` を入れるとセル数分のオブジェクトが生成されるため、`r * w + c` で1次元インデックスに変換し、`IntArray` キュー（`q`, `hd`, `tl`）に格納することでメモリとGC負荷を最小化しました。

#### 14. レートリミッター＆LRUキャッシュ（`領域11_実務型状態遷移_レートリミッターとキャッシュ制御.kt`）
* **Q. 本番環境でこのレートリミッターを動かす場合、このインメモリ実装の課題は何ですか？**
  * **A.** 2点あります。1点目は複数サーバーや複数スレッド間で同期されないこと、2点目は一度だけアクセスして離脱したユーザーのキーが `HashMap` に残り続けてメモリリーク（OOM）を起こすことです。実務の分散環境ではRedisのSorted Set（Luaスクリプト）を用い、クライアント内のローカル制御であればキー数上限付きの `LruCache` と組み合わせます。

#### 15. 約数列挙とGCD（`領域12_整数論と周期性_約数列挙とユークリッド互除法.kt`）
* **Q. 約数列挙で `d` を `Int` ではなく `Long`（`1L`）にしているのはなぜですか？ 入力 `N` は `Int` ですよね？**
  * **A.** `N` が `Int.MAX_VALUE`（$2,147,483,647$）のとき、$\sqrt{N} \approx 46,340.95$ です。`d = 46,341` になった瞬間、`Int` 同士の掛け算 `d * d` は `Int.MAX_VALUE` を超えて負の数にオーバーフローし、無限ループ（TLE）に陥るため、必ず `Long` で比較しています。

#### 16. バグ修正問題（Bugfixingタスク）に対する面接尋問
* **Q. このバグ修正問題で、なぜ別の箇所ではなくこの行（例：初期値やループ終端条件）を修正したのですか？ 実務でこのバグが起きないようテストを書くならどんなケースを書きますか？**
  * **A.** まず最小要素数（$N=1$）と、条件が配列の先頭（`i=0`）および末尾（`i=N-1`）で成立するケースを机上トレースし、ループ不変条件がどこで破綻しているかを特定しました。実務の単体テストでは、①要素数1、②全要素が同一（すべて0 / すべて1 / すべて負数）、③最大値が先頭にあるケース、④最大値が末尾にあるケースの4つの境界値パラメータ化テスト（ParameterizedTest）を必ず追加して回帰を防ぎます。

#### 17. Android実務実装タスク①（ViewModel + Coroutines + StateFlow）に対する面接尋問
* **Q. 実装してもらった `ViewModel` で、キャッシュ保存時に `repo.search(q).toList()` とコピーしている理由と、Process Death対策を教えてください。**
  * **A.** 呼び出し元やリポジトリから返されたリストが内部的に `MutableList` だった場合、後から外部で書き換えられるとキャッシュとUI状態の不変性（Immutability）が壊れて `DiffUtil` 等が正しく動かなくなるため、`.toList()` で防御的イミュータブルコピーを行っています。またOSによるProcess Death対策としては、`SavedStateHandle` をコンストラクタ注入し、`savedStateHandle.getStateFlow("query", "")` で検索クエリを復元する設計にします。

#### 18. Android実務実装タスク②（RecyclerView.Adapter / DiffUtil / Form Validation）に対する面接尋問
* **Q. `RecyclerView` の `onBindViewHolder` で `else` ブロックを明示的に書いている理由と、チラつき防止策を教えてください。**
  * **A.** `RecyclerView` はスクロールアウトした `ViewHolder` のインスタンスを使い回すため、`if` 条件だけで `View.VISIBLE` や背景色を変更すると、再利用された別アイテムに前の表示状態が残るバグが起きます。これを防ぐために `else` で必ず初期状態へリセットしています。また一部だけの更新でのチラつきを防ぐには、`DiffUtil.ItemCallback.getChangePayload` で差分フィールドだけを返し、`onBindViewHolder(holder, position, payloads)` で該当Viewだけを更新します。

#### 19. Android実務実装タスク③（OkHttp Interceptor / 単体テスト）に対する面接尋問
* **Q. 実装した `Interceptor` で401のときに `synchronized(lock)` と `res.close()` を入れている意図を教えてください。**
  * **A.** 2点あります。1点目は、リトライの `chain.proceed()` を呼ぶ前に最初の `res.close()` を呼ばないと、最初のレスポンスのTCPソケット/ストリームが解放されずコネクションリークを起こすためです。2点目は、並列通信中に複数のリクエストが同時に401を受けた際、全員が `refreshAccessToken()` を重複実行しないよう `synchronized` と「リクエスト時のトークン `tok` と現在の最新トークン `cur` の比較（Double-Checked Locking）」で1回だけリフレッシュさせるためです。
