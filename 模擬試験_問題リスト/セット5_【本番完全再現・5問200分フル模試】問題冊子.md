## Task 1：【Bugfixing（バグ修正問題）】通知バッジの最長連続アクティブ日数（目標：15分）

### 問題文
あるAndroidアプリで、過去 $N$ 日間のユーザのログイン状態を表す配列 `A`（要素は `0` または `1`）が与えられます。`1` はログインした日、`0` はログインしなかった日を表します。
以下の関数 `solution(A: IntArray): Int` は、`1` が最も長く連続した日数（最大連続ログイン日数）を返すよう実装されましたが、**バグが含まれており一部のケースで誤った結果を返します**。

**【絶対制約】**:
既存のコードのうち、**最大2行まで（at most 2 lines）** を変更してバグを修正してください。関数全体を書き直した場合は0点となります。

```kotlin
import kotlin.math.max

fun solution(A: IntArray): Int {
    var maxSpan = 0
    var currentSpan = 0
    for (i in 1 until A.size) {
        if (A[i] == 1) {
            currentSpan += 1
        } else {
            maxSpan = max(maxSpan, currentSpan)
            currentSpan = 0
        }
    }
    return maxSpan
}
```

### 制約
- $N$ は $1 \sim 100,000$ の整数
- `A` の各要素は `0` または `1`
- 目標計算量：時間 $O(N)$、空間 $O(1)$

## Task 2：【アルゴリズム（標準）】プッシュ通知の同一チャンネル・クールダウン制御（目標：35分）

### 問題文
ニュース配信Androidアプリにおいて、短時間に同じチャンネルの通知が連続して鳴るのを防ぐ「クールダウン機構」を検証します。
時系列順に並んだ $N$ 件の通知イベントがあり、$i$ 番目の通知は時刻 `T[i]`（秒）にチャンネルID `C[i]` へ届きます（配列 `T` は広義単調増加：`T[0] <= T[1] <= ... <= T[N-1]`）。

クールダウン時間を `D` 秒としたとき、各通知は以下のルールで判定されます：
- 同じチャンネル `C[i]` において、**前回「配信成功（Delivered）」となった通知の時刻から `D` 秒以上経過している場合**（すなわち `今回の時刻 - 前回配信成功した時刻 >= D`）、またはそのチャンネルで初めての通知である場合、今回の通知は **「配信成功」** となります。
- そうでない場合（前回配信成功した時刻からの経過時間が `D` 秒未満の場合）、今回の通知は **「抑制（ミュート）」** され、配信されません（※抑制された通知は「前回配信成功した時刻」を更新しない点に注意してください）。

すべての通知を順番に処理したとき、**最終的に「配信成功」となった通知の総数**を返す関数を実装してください。

```kotlin
fun solution(T: IntArray, C: IntArray, D: Int): Int
```

### 入力例
- `T = [1, 3, 6, 10, 11]`, `C = [10, 10, 10, 20, 20]`, `D = 5` の場合：
  - $i = 0$（時刻1, ch 10）：初回なので **配信成功**（ch 10の最終配信時刻 = 1）
  - $i = 1$（時刻3, ch 10）：$3 - 1 = 2 < 5$ なので抑制（ch 10の最終配信時刻は 1 のまま）
  - $i = 2$（時刻6, ch 10）：$6 - 1 = 5 \ge 5$ なので **配信成功**（ch 10の最終配信時刻 = 6）
  - $i = 3$（時刻10, ch 20）：初回なので **配信成功**（ch 20の最終配信時刻 = 10）
  - $i = 4$（時刻11, ch 20）：$11 - 10 = 1 < 5$ なので抑制
  - 配信成功の総数は **3** を返します。

### 制約
- $N$ は $0 \sim 100,000$ の整数
- `T[i]` は $0 \sim 1,000,000,000$ の整数（昇順ソート済み）
- `C[i]` は $1 \sim 1,000,000,000$ の整数
- `D` は $1 \sim 1,000,000,000$ の整数
- 目標計算量：時間 $O(N)$、空間 $O(N)$

## Task 3：【アルゴリズム（応用）】オフライン記事パックの分割ダウンロード最小帯域幅（目標：40分）

### 問題文
オフラインリーダーアプリで、順序通りに並んだ $N$ 個のチャンク（サイズ配列 `S[0..N-1]` KB）を、最大 `K` 回のバッチ通信に分けて順番にダウンロードします。
1回のバッチ通信では、連続する1つ以上のチャンクをまとめてダウンロードできます（チャンクの順序を入れ替えることはできません）。

アプリのピークメモリ消費を抑えるため、**「1回のバッチ通信でダウンロードするチャンクサイズの合計」の最大値** をできるだけ小さくしたいと考えています。
$N$ 個のチャンクを最大 `K` 個の連続ブロックに分割したとき、**最大ブロック和の最小値** を求めてください。
ただし、`S` の合計は `Int.MAX_VALUE` を超える可能性があるため、戻り値は `Long` とします。

```kotlin
fun solution(K: Int, S: IntArray): Long
```

### 入力例
- `K = 3`, `S = [200, 100, 500, 100, 200, 200, 200]` の場合：
  - `[200, 100]`, `[500]`, `[100, 200, 200, 200]` の3ブロックに分割すると、各ブロックの合計は `300`, `500`, `700` となり最大値は `700`。
  - `[200, 100, 500]`, `[100, 200, 200]`, `[200]` なら最大値は `800`。
  - `[200, 100]`, `[500, 100]`, `[200, 200, 200]` と分割すると、各ブロックの合計は `300`, `600`, `600` となり、最大値は **600**（これが最小）を返します。

### 制約
- $N$ は $1 \sim 100,000$ の整数
- $K$ は $1 \sim N$ の整数
- `S[i]` は $1 \sim 100,000,000$ の整数
- 目標計算量：時間 $O(N \log(\sum S))$、空間 $O(1)$

## Task 4：【Android実務実装①】ViewModel + Coroutines + StateFlow による記事検索＆インメモリキャッシュ制御（目標：50分）

### 問題文
Androidアプリの検索画面を担当する `ArticleSearchViewModel` を実装してください。
以下のインターフェースおよび状態定義が与えられています。

```kotlin
import kotlinx.coroutines.CoroutineDispatcher
import kotlinx.coroutines.Dispatchers
import kotlinx.coroutines.flow.StateFlow

data class Article(val id: Long, val title: String)

interface ArticleRepository {
    suspend fun searchArticles(query: String): List<Article>
}

sealed interface SearchUiState {
    object Idle : SearchUiState
    object Loading : SearchUiState
    data class Content(val query: String, val articles: List<Article>, val fromCache: Boolean) : SearchUiState
    data class Empty(val query: String) : SearchUiState
    data class Error(val query: String, val message: String) : SearchUiState
}
```

### 実装仕様（採点テスト項目）
1. **初期状態**: `uiState: StateFlow<SearchUiState>` の初期値は `SearchUiState.Idle` とすること。
2. **クエリの正規化とバリデーション**:
   - `onQuerySubmitted(rawQuery: String)` が呼ばれたら、前後の空白を除去（`trim()`）する。
   - トリム後の文字列が **2文字未満** の場合は、リポジトリを呼ばず（進行中の検索があればキャンセルし）、状態を `SearchUiState.Error(trimmedQuery, "Query too short")` に遷移させること。
3. **インメモリキャッシュ機構（`forceRefresh: Boolean = false`）**:
   - `onQuerySubmitted(rawQuery: String, forceRefresh: Boolean = false)` において、過去に成功した検索結果がキャッシュに存在し、かつ `forceRefresh == false` の場合は、**`Loading` を経由せず、リポジトリも呼ばずに即座に** キャッシュされたリストを使って `SearchUiState.Content(trimmedQuery, cachedList, fromCache = true)`（または0件なら `SearchUiState.Empty(trimmedQuery)`）を発行すること。
4. **非同期通信とキャンセル制御**:
   - キャッシュミスまたは `forceRefresh == true` の場合、古い検索ジョブが実行中であればキャンセルし、`SearchUiState.Loading` を発行した上で `repository.searchArticles(trimmedQuery)` を呼び出す。
   - 結果が空リストなら `SearchUiState.Empty(trimmedQuery)`、1件以上なら `SearchUiState.Content(trimmedQuery, list, fromCache = false)` を発行し、結果をキャッシュに保存する。
   - 例外が発生した場合は、`CancellationException` は再スローし、その他の例外は `SearchUiState.Error(trimmedQuery, e.message ?: "Network error")` に遷移させること。
5. **`clearCache()` メソッド**:
   - 保持しているキャッシュをすべて消去し、状態を `SearchUiState.Idle` に戻すこと。

## Task 5：【Android実務実装②】OkHttp 認証＆レート制限リトライ Interceptor の実装（目標：45分）

### 問題文
API通信を行うAndroidクライアント向けに、以下の仕様を満たす OkHttp の `Interceptor`（`ResilientAuthInterceptor`）を実装してください。

```kotlin
interface AuthSessionManager {
    fun getCurrentToken(): String?
    fun refreshToken(): String?
    fun onSessionExpired()
}
```

### 実装仕様（採点テスト項目）
1. **認証ヘッダの自動付与**:
   - `authSessionManager.getCurrentToken()` が非nullかつ非空文字の場合、リクエストヘッダに `Authorization: Bearer <token>` を付与する（すでに同名ヘッダがある場合は上書きする）。
2. **401 Unauthorized 時の1回限りトークンリフレッシュ＆リトライ**:
   - 最初のレスポンスコードが `401` だった場合、`authSessionManager.refreshToken()` を呼び出す。
   - 新しいトークン（非nullかつ非空文字）が取得できた場合は、**最初のレスポンスを必ず `close()` した上で**、新しいトークンを `Authorization: Bearer <newToken>` にセットして1回だけ再リクエスト（`chain.proceed`）を行い、その結果を返す。
   - もし `refreshToken()` が `null` または空文字を返した場合、あるいはリトライ後のレスポンスも再び `401` だった場合は、`authSessionManager.onSessionExpired()` を1回呼び出し、そのレスポンスをそのまま返す。
3. **503 Service Unavailable 時の1回限り即時リトライ**:
   - 最初のレスポンスコードが `503` だった場合、**最初のレスポンスを `close()` した上で**、同じリクエストを1回だけ再試行（`chain.proceed`）してその結果を返す。
